\docTitle{Web Explorers}
\phantomsection\label{docstart:web_model_explorer}

This document describes the local web explorers used to inspect \name{} runs and generated question bundles.

\section*{Model Explorer}

The Web Model Explorer is a local, read-only browser for inspecting resolved run graphs, materialized Simulink runs, eligibility metrics, and generated candidate pools.

Start it from the repository with:

\begin{DocCode}
bash web_model_explorer/start.sh
\end{DocCode}

The launcher starts the Next.js app in \code{web_model_explorer/}.
It uses \code{0.0.0.0:3001} by default.
\code{WEB_MODEL_EXPLORER_HOST}, \code{WEB_MODEL_EXPLORER_PORT}, and \code{WEB_MODEL_EXPLORER_RUNS_DIR_NAME} can override the host, port, and displayed run-artifact folder.

\section*{What It Shows}

The sidebar lists allowed \name{} models that exist under \code{models/simulink/}.
Models with missing required files remain listed but show a warning badge.
The header shows the selected model, selected \code{policy_id}, active runs folder name, and a reload button that re-reads registry and distribution files from disk.

The main table is organized by \code{family_id} from the resolved run graph.
Each family can be expanded to show its baseline run, intervention runs, and matched time-zero/static-change probe runs.

Table columns include:

\begin{itemize}
\item status from \code{model_record.json};
\item eligibility from \code{eligibility_metrics.jsonl};
\item \code{run_id};
\item \code{family_id};
\item \code{source};
\item \code{validation_profile};
\item \code{recipe_hash};
\item exposed parameter and initial-state values in experiment-config order;
\item actions for plotting and expansion.
\end{itemize}

Expanded intervention rows show changed parameter, direction, new value, and intervention time from \code{run_nodes.jsonl} and \code{run_edges.jsonl}.

\section*{Plot Area}

The plot area renders selected runs.
Plot data can be shown with no noise or with a model-provided low or high noise profile when \code{noise_adder.py} exists.

Controls include:

\begin{itemize}
\item run-selection eye buttons in the table;
\item noise profile: \code{none}, \code{low}, or \code{high};
\item deterministic noise seed;
\item observed signal selection.
\end{itemize}

If two runs are selected and noise is enabled, the UI may show per-signal SNR values using the model noise-adder utilities.

\section*{Deep Links}

Deep links can preselect a model, policy, run, and optional comparator.
Supported query parameters include:

\begin{DocCode}
model, policy, run, run2, compare_run, compare, noise_profile, noise_seed
\end{DocCode}

The \code{compare} parameter may be \code{baseline}, \code{time0}, \code{sibling}, or \code{none}.
A plain \code{?run=<RUN_ID>} link opens a single-run view unless an explicit comparator is provided.

Shortcut:

\begin{DocCode}
http://localhost:3001/<run_id>
\end{DocCode}

opens the matching run directly if it can be located.

\section*{Endpoints Used}

\begin{itemize}
\item \code{GET /api/models}: read allowed models and validation warnings.
\item \code{GET /api/policies?model=<MODEL>}: list available resolved plans under \code{plans/}.
\item \code{GET /api/registry?model=<MODEL>&policy=<POLICY_ID>}: load resolved run graph, runtime status, eligibility metrics, signal display names, noise profiles, and metadata.
\item \code{GET /api/distribution?model=<MODEL>}: load \code{experiment_config.json} and generated metadata used for legal domains and sampling details.
\item \code{GET /api/locate-run?run=<RUN_ID>}: resolve a deep-linked run identifier to model and policy.
\item \code{GET /api/data?model=<MODEL>&run=<RUN_ID>&max_rows=<N>&noise_profile=<PROFILE>&noise_seed=<SEED>}: load a run artifact for plotting.
\item \code{GET /api/simulate?model=<MODEL>&policy=<POLICY_ID>}: read saved simulation status information when present.
\end{itemize}

\section*{Files Read}

\begin{itemize}
\item \code{models/simulink/<MODEL>/plans/<policy_id>/run_nodes.jsonl}
\item \code{models/simulink/<MODEL>/plans/<policy_id>/run_edges.jsonl}
\item \code{models/simulink/<MODEL>/plans/<policy_id>/generation_report.json}
\item \code{models/simulink/<MODEL>/plans/<policy_id>/validation_report.json}
\item \code{models/simulink/<MODEL>/<runs>/model_record.json}
\item \code{models/simulink/<MODEL>/metrics/<policy_id>/eligibility_metrics.jsonl}
\item \code{models/simulink/<MODEL>/generated/metadata.json}
\item \code{models/simulink/<MODEL>/description_levels.json}
\item \code{models/simulink/<MODEL>/experiment_config.json}
\item \code{models/simulink/<MODEL>/<runs>/<run_id>/data.parquet}
\item \code{tsENV_questions/<MODEL>/dataframes/<run_id>.parquet}, as fallback for exported bundles
\item \code{models/simulink/<MODEL>/noise_adder.py}
\end{itemize}

During migration, the explorer may read a legacy \code{model_run_specs.json} compatibility artifact, but the resolved run graph is the preferred source of truth.

\section*{Web Human Study}

The Web Human Study app checks whether exported questions are feasible for humans.
It reads from \code{tsENV_questions/} and can be started with:

\begin{DocCode}
bash web_human_study/start.sh [--port PORT]
\end{DocCode}

The app visualizes time series with Plotly and shows the multiple-choice labels from \code{questions.json}.
When a user selects an option, the correct label is shown, and the result is saved under \code{human_feedback/<name>.json}.
There is also a button to mark a question as problematic.

Shortcut forms include:

\begin{itemize}
\item \code{http://localhost:5173/<run_id>} or \code{<sample_uuid>}: open a sample.
\item \code{http://localhost:5173/<question_id>}: open a question.
\item \code{http://localhost:5173/<question_id>-<sample_uuid>}: open a specific sample within a question.
\end{itemize}
