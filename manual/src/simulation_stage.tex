\docTitle{Stage: Simulate}
\phantomsection\label{docstart:simulation_stage}
This stage converts resolved Simulink run recipes into materialized time-series artifacts using the Simulink/Simscape engine.
The step is computationally expensive: a resolved policy may contain tens or hundreds of thousands of runs, and the resulting artifacts can occupy many tens of gigabytes.
To speed up data generation, the stage supports parallel execution with MATLAB's Parallel Computing Toolbox and partial regeneration of only missing, failed, or stale runs.
The stage is exposed as a single script, however internally has two main steps.
First, it reconciles the resolved plan with the runtime inventory in \code{model_record.json}, so it only simulates runs that are pending, failed, or stale.
Second it runs the simulations. 
Note that when MATLAB parallelism is enabled, it prepares isolated per-run MATLAB workspaces and submits them to a MATLAB \code{parpool}.
Each workspace contains a \code{simulink_model.mdl} with the initial parameters, the simulation entrypoint, and the time-varying parameter payload for one run.
Prepared workspaces are operational scratch state, not final benchmark artifacts.
They can be large and can create heavy small-file I/O, so large batches should place them on scratch storage via \code{TMPDIR} or an explicit prepared workspace root.
The final artifacts are written separately under \code{models/simulink/<simulator_id>/runs/<run_id>/}.

\subsection*{Prepared Workspace Cost and Reuse}
For large policies, workspace preparation can dominate startup time.
In one BallDrop run, preparing 128,806 per-run MATLAB workspaces took roughly 125 minutes, about 17.2 prepared runs per second.
This cost is separate from MATLAB simulation time.

To avoid repeating this work after an interrupted or stuck MATLAB job, the runner can preserve or reuse prepared workspaces; see \hyperref[sec:simulate-cli-options]{the command-line options}.

\section*{Invocation}

The script is \code{workflows/simulate/run_pending_sims.py}.
It reads a resolved run graph from \code{plans/<policy_id>/run_nodes.jsonl} and \code{plans/<policy_id>/run_edges.jsonl}, validates the extracted \termSimulator metadata, reconciles the requested run nodes with \code{model_record.json}, and launches MATLAB only for runs that are pending, failed, or stale.
A run is stale when it is marked \code{success}, but its artifact is missing or its stored recipe/parameter hash no longer matches the selected resolved plan.
The script can run multiple runs in parallel for one \termSimulator by starting a MATLAB \code{parpool}; separate \termSimulators may be launched as separate jobs.

\begin{DocCode}
SIMSCAPE_CUSTOM_PATH=... \
TMPDIR=... \
TSENV_MATLAB_PARPOOL_CHUNK_SIZE=... \
TSENV_MATLAB_FUTURE_TIMEOUT_S=... \
TSENV_MATLAB_WORKER_START_STAGGER_S=... \
python workflows/simulate/run_pending_sims.py \
  [--model SIMULATOR] \
  --policy POLICY_ID \
  [--matlab-workers N] \
  [--overwrite] \
  [--rerun-failed] \
  [--raise-on-errors] \
  [--debug] \
  [--run-id RUN_ID] \
  [--runs-root RUNS_ROOT] \
  [--matlab-cache-root MATLAB_CACHE_ROOT] \
  [--prepared-workspace-root PREPARED_WORKSPACE_ROOT] \
  [--keep-prepared-workspace] \
  [--profile-timing] \
  [--compute-features [FEATURE1 ...]]
\end{DocCode}

\phantomsection\label{sec:simulate-cli-options}
\begin{itemize}
\item \code{--model}: selected \termSimulator. If omitted, the script iterates over \hyperref[sec:allowed-tsenv-models]{all
allowed \name{} \termSimulators}.
\item \code{--policy}: policy identifier. The script reads the resolved run graph under \code{models/simulink/<simulator_id>/
plans/<policy_id>/}.
\item \code{--matlab-workers}: number of MATLAB \code{parpool} workers. The default is \code{1}. Values greater than \code{1}
require MATLAB's Parallel Computing Toolbox.
\item \code{--overwrite}: mark all selected runs as \code{not_run} and materialize them again.
\item \code{--rerun-failed}: mark only selected runs currently recorded as \code{failed} as \code{not_run} and materialize them
again.
\item \code{--raise-on-errors}: fail immediately instead of recording \code{failed} status.
\item \code{--debug}: persist per-run debug artifacts under \code{runs/<run_id>/debug/}.
\item \code{--run-id}: materialize only the specified \code{RUN_ID}. The run must appear in the selected \code{--policy}.
\item \code{--runs-root}: optional base directory for final run artifacts. When set, each \termSimulator writes to
\code{RUNS_ROOT/<simulator_id>/runs/}.
\item \code{--matlab-cache-root}: optional base directory for MATLAB/Simulink generated cache files. If omitted, MATLAB uses its
normal cache and preference locations.
\item \code{--prepared-workspace-root}: prepared MATLAB workspace root to use now. If it already contains prepared jobs,
preparation is skipped; otherwise the runner prepares into this root and preserves it.
\item \code{--keep-prepared-workspace}: preserve an automatically created prepared workspace root after the run, so it can be
reused later with \code{--prepared-workspace-root}.
\item \code{--profile-timing}: write per-phase timing records to \code{profile_timing.jsonl} in the selected run root.
\item \code{--compute-features}: compute \code{features.json}. Optional feature names must match the \termSimulator-specific
\code{features.py}. By default, no features are computed.
\end{itemize}

\code{SIMSCAPE_CUSTOM_PATH} must point to the directory containing custom Simscape blocks.
For large parallel batches, set \code{TMPDIR} to node-local scratch so prepared MATLAB workspaces are not created under a small
system temporary directory.

\begin{DocCode}
SIMSCAPE_CUSTOM_PATH=/csem/divr/users/tbe/repo/tsENV/simscape_custom
TMPDIR=/scratch/tbe/tsenv_tmp
\end{DocCode}

The parallel MATLAB runner also accepts these environment variables:

\begin{itemize}
\item \code{TSENV_MATLAB_PARPOOL_CHUNK_SIZE}: number of jobs submitted to MATLAB per chunk.
\item \code{TSENV_MATLAB_FUTURE_TIMEOUT_S}: per-running-future timeout. A timed-out future is canceled and recorded as failed
instead of blocking the entire chunk.
\item \code{TSENV_MATLAB_WORKER_START_STAGGER_S}: small per-worker-slot delay before simulation starts, used to reduce
simultaneous Simulink/Simscape initialization pressure.
\end{itemize}

\section*{Internal Steps}

The code validates inputs, reconciles \code{model_record.json}, and then materializes selected runs.
The following applies to all run kinds: baseline, intervention, and time-zero/static-change runs.
Each run is materialized independently and tracked independently in \code{model_record.json}.

\subsection*{Validation Between \code{metadata.json}, \code{experiment_config.json}, and \code{description_levels.json}}

The stage validates the checks described in \hyperref[sec:environment-validation-rules]{the environment validation rules}.

\subsection*{Reconciliation Flow}

The script reconciles \code{run_nodes.jsonl} with \code{runs/model_record.json} as follows:

\begin{enumerate}
\item Load the resolved run nodes for \code{--policy} and build a map:
\begin{DocCode}
run_id -> recipe_hash
\end{DocCode}
\item Validate that every requested \code{run_id} has a unique \code{recipe_hash}, a valid \code{run_type}, and a recipe that satisfies the hard constraints in \code{experiment_config.json}.
\item For every run node in the selected plan, ensure that \code{model_record.json} contains a corresponding entry. Missing entries are created with status \code{not_run}.
\item If \code{--overwrite} is passed, mark every selected run as \code{not_run}.
\item If \code{--rerun-failed} is passed, mark only failed selected runs as \code{not_run}.
\item If \code{--run-id} is passed, restrict all later reconciliation and materialization to that single run.
\item If a run is currently marked as \code{success}, downgrade it to \code{not_run} if \code{runs/<run_id>/data.parquet} does not exist or if \code{model_record.json::<run_id>.recipe_hash} does not match \code{run_nodes.jsonl::<run_id>.recipe_hash}.
\item If a run is set to \code{not_run}, delete \code{runs/<run_id>/} before re-materialization.
\item By default, do not delete run folders that are outside the selected plan. Since run IDs are content-addressed, the same run may be reused by multiple policies. Pruning unknown folders is allowed only under an explicit cleanup flag.
\end{enumerate}

If no selected run remains in \code{not_run}, the stage rewrites \code{model_record.json} and exits without launching MATLAB.

\subsection*{Simulation Flow}

After reconciliation, the stage executes every selected run marked as \code{not_run}.
Serial and parallel execution share the same logical pipeline, but differ in how the MATLAB simulation is launched.
Serial mode materializes one run at a time.
Parallel mode prepares per-run MATLAB workspaces, runs MATLAB jobs through a \code{parpool}, and then finalizes each completed chunk in Python.

\begin{enumerate}
\item Prepare the canonical runtime recipe for the run.
The resolved node supplies \code{kind}, \code{baseline_parameters}, optional intervention parameter/value/time, sampling rates,
and \code{end_time_input_s}.
The top-level \code{kind} determines how the simulator applies the intervention: baseline nodes have no intervention,
intervention nodes apply the changed value at \code{intervention.time}, and time-zero/static-change nodes apply the changed
value from time zero.

\item Run the Simulink/Simscape model and collect raw observable signals.
In serial mode, the runner materializes one run at a time.
In parallel mode, MATLAB workers run \code{sim_the_model.m} from prepared per-run workspaces, and Python receives raw MATLAB
results for each completed chunk.

\item Extract and normalize the raw signals returned by MATLAB.
The runner keeps only configured observable signals and converts Simulink and Simscape outputs into the common signal dictionary
used by the Python finalization path.

\item If requested, compute problem-specific features with \code{features.py::compute_problem_specific_features(...)} and save
the result as \code{features.json}. Missing scalar features are stored as JSON \code{null}; missing list-valued features are
stored as empty lists.

\item Resample the signal dictionary to the configured output sampling rate.
The first timestamp is expected to be \code{dt = 1/sampling_rate_hz}; the last point must be smaller than
\code{end_time_input_s}.

\item Serialize \code{data.parquet} under \code{runs/<run_id>/} and validate the saved artifact.
Validation checks timestamp spacing, column order, \code{float32} storage, minimum length, expected sample count, and absence of
\code{NaN} or \code{inf} values.
\end{enumerate}

\subsection*{Parallel Execution}

When \code{--matlab-workers} is set to \code{1}, runs are materialized serially.
When \code{--matlab-workers} is greater than \code{1}, the script starts one MATLAB engine session and creates a MATLAB \code{parpool("Processes", N)}.
Each pool worker is a separate MATLAB process.

Before submitting jobs to the pool, the runner prepares one isolated MATLAB workspace per selected run.
Each prepared workspace contains a run-specific \code{simulink_model.mdl}, \code{sim_the_model.m}, and \code{time_varying_parameters.mat}.
The copied model file has the run's initial workspace parameters embedded.
These prepared workspaces are operational scratch state and are separate from the final \code{runs/<run_id>/} artifacts.

Jobs are submitted to MATLAB in chunks.
The chunk size is controlled by \code{TSENV_MATLAB_PARPOOL_CHUNK_SIZE}; if unset, the runner derives a chunk size from the worker count.
After each chunk returns, Python extracts signals, serializes successful runs, validates artifacts, updates \code{model_record.json}, and writes the registry to disk.
This means completed chunks survive later failures or interruption.

\begin{DocCode}
TSENV_MATLAB_PARPOOL_CHUNK_SIZE=8
TSENV_MATLAB_FUTURE_TIMEOUT_S=3600
TSENV_MATLAB_WORKER_START_STAGGER_S=0.1
\end{DocCode}

\code{TSENV_MATLAB_FUTURE_TIMEOUT_S} sets a per-running-future timeout in seconds.
If a MATLAB future exceeds this timeout, the runner cancels that future and records the corresponding run as \code{failed} instead of blocking the whole chunk indefinitely.
Set it to \code{0} to disable the timeout.

\code{TSENV_MATLAB_WORKER_START_STAGGER_S} adds a small per-worker-slot delay before each worker enters the simulation.
This reduces simultaneous Simulink/Simscape model-load pressure when many workers start at once.

\subsection*{Prepared Workspace Reuse}

For large policies, workspace preparation can be expensive.
If a job is interrupted after preparation, a later run can reuse the prepared root with \code{--prepared-workspace-root}.
If that root already contains prepared jobs, the runner skips the preparation pass and submits the existing jobs to MATLAB.
Use \code{--keep-prepared-workspace} when starting a new run if the prepared root should be preserved for later recovery.

Prepared roots placed under node-local \code{/scratch} are only valid on the node where they were created.
When relaunching an LSF job that reuses such a root, pin the job to that host, for example with \code{bsub -m l7161}.
If the scheduler starts the job on another host, the \code{/scratch} path may be missing or may refer to different local storage.

\begin{DocCode}
bsub -q normal -m l7161 -n 8 -J ball_drop_reuse_l7161 \
  -o logs/lsf/ball_drop_reuse_l7161.%J.out \
  -e logs/lsf/ball_drop_reuse_l7161.%J.err \
  "cd /csem/divr/users/tbe/repo/tsENV && \
   export TMPDIR=/scratch/tbe/tsenv_tmp && \
   export SIMSCAPE_CUSTOM_PATH=/csem/divr/users/tbe/repo/tsENV/simscape_custom && \
   export TSENV_MATLAB_PARPOOL_CHUNK_SIZE=8 && \
   export TSENV_MATLAB_FUTURE_TIMEOUT_S=3600 && \
   export TSENV_MATLAB_WORKER_START_STAGGER_S=0.1 && \
   env/bin/python workflows/simulate/run_pending_sims.py \
     --model BallDrop \
     --policy ball_drop_10000_families_v1 \
     --matlab-workers 8 \
     --rerun-failed \
     --profile-timing \
     --prepared-workspace-root /scratch/tbe/tsenv_tmp/tsenv-sim-parpool-BallDrop-..."
\end{DocCode}

Use \code{--profile-timing} to compare worker counts on the target machine.
The end-to-end wall time should be compared together with \code{profile_timing.jsonl} phases:
\code{matlab_parpool_simulations} measures the submitted MATLAB chunk time, while \code{parallel_materialization} includes preparation and Python-side post-processing.
For a fair test, run the same policy into separate \code{--runs-root} directories and compare successful \code{data.parquet} counts as well as wall time.

\section*{Output Artifacts}

By default, materialized artifacts are stored under:

\begin{DocCode}
models/simulink/<simulator_id>/runs/<run_id>/
\end{DocCode}

When \code{--runs-root} is provided, artifacts are stored under:

\begin{DocCode}
<RUNS_ROOT>/<simulator_id>/runs/<run_id>/
\end{DocCode}

Each successful run directory contains:

\begin{itemize}
\item \code{recipe.json}: the exact canonical recipe copied from \code{run_nodes.jsonl}.
\item \code{data.parquet}: the materialized time series.
\item \code{simulink_model.mdl}: the exact Simulink model used to generate this run.
\item \code{features.json}: optional problem-specific feature dictionary computed from \code{observable_signals}. This file is omitted when \code{--compute-features} is not passed.
\end{itemize}

If \code{--debug} is passed, each successful run directory also contains:

\begin{itemize}
\item \code{debug/input_signals.mat}: MATLAB payload storing \code{TimeVaryingParameters}.
\item \code{debug/tsenv_worker_heartbeat.jsonl}: stage transitions recorded by the MATLAB worker.
\item \code{debug/tsenv_worker_stage.txt}: latest recorded MATLAB worker stage.
\end{itemize}

\code{model_record.json} is rewritten under the run root and serves as the runtime inventory of completed, pending, or failed run IDs.
Any validation error or simulation error records a failed run unless \code{--raise-on-errors} is passed.

\section*{Validation Rules}

In addition to run-specific validation, the stage enforces:

\begin{itemize}
\item every selected \code{run_id} must appear in \code{runs/model_record.json};
\item every \code{success} entry for a selected run must have a corresponding \code{runs/<run_id>/data.parquet} artifact;
\item every stored \code{recipe_hash} in \code{model_record.json} must match the \code{recipe_hash} in \code{run_nodes.jsonl};
\item every persisted \code{recipe.json} must match the selected run node's canonical recipe;
\item if MATLAB worker parallelism is enabled, materializing the same selected runs with one worker and with multiple workers must produce equivalent \code{recipe.json}, \code{data.parquet}, and success/failure records;
\item run folders outside the selected plan must not be deleted unless an explicit cleanup mode is enabled.
\end{itemize}

\section*{Troubleshooting: MathWorks Online Licensing State}

If Stage: Simulate cannot start MATLAB even though the MATLAB installation is present, check for stale MathWorks online-licensing state in the user's home directory.

\end{DocCode}

\section*{\code{model_record.json} Schema}

\begin{DocCode}
{
  "<run_id>": {
    "run_type": "baseline|intervention|time0_baseline",
    "family_id": "<family_id>",
    "recipe_hash": "<32-hex-hash>",
    "status": "not_run|success|failed",
    "timestamp": "...",
    "last_policy_id": "<policy_id>",
    "class_internal": "gravity|mass|...|no_intervention|",
    "class_agent_facing_name": "gravity|mass|...|no intervention|"
  }
}
\end{DocCode}

The \code{recipe_hash} field is copied from \code{run_nodes.jsonl}.
The runtime inventory does not define the recipe; it only records the materialization status of a recipe whose canonical definition lives in the resolved run graph.
