\docTitle{Stage: Simulate}
\phantomsection\label{docstart:simulation_stage}

This stage converts resolved Simulink run recipes into materialized run artifacts.

The main driver is \code{workflows/simulate/run_pending_sims.py}.
It reads a resolved run graph from \code{plans/<policy_id>/run_nodes.jsonl} and \code{plans/<policy_id>/run_edges.jsonl}, checks the extracted \termSimulator metadata, reconciles the requested run nodes with the runtime inventory on disk, and launches MATLAB only for runs that are pending, failed, or stale.
Stale means that status says success, but the artifact is missing or was produced for an older/different recipe/parameters hash.

A resolved run graph is the concrete output of the candidate-generation stage: all random sampling decisions have already been made, every run has a stable \code{run_id}, and every baseline/intervention/time-zero relationship is explicit.
Stage: Simulate does not sample new runs; it only materializes these resolved recipes.

The stage can be launched concurrently for different \termSimulators.
Additionally, if MATLAB's Parallel Computing Toolbox is installed, the script supports running multiple runs in parallel within the same \termSimulator by starting a MATLAB \code{parpool} with \code{N} workers.

\section*{Invocation}

\begin{DocCode}
python workflows/simulate/run_pending_sims.py \
  [--model SIMULATOR] \
  [--matlab-workers N] \
  --policy POLICY_ID \
  [--overwrite] \
  [--rerun-failed] \
  [--raise-on-errors] \
  [--debug] \
  [--run-id RUN_ID] \
  [--runs-root RUNS_ROOT] \
  [--matlab-cache-root MATLAB_CACHE_ROOT] \
  [--profile-timing] \
  [--compute-features [FEATURES1 ...]]
\end{DocCode}

\begin{itemize}
\item \code{--model}: selected \termSimulator. If omitted, the script iterates over \hyperref[sec:allowed-tsenv-models]{all allowed \name{} \termSimulators}.
\item \code{--matlab-workers}: number of MATLAB \code{parpool} workers. The default is \code{1}, which runs one simulation at a time and does not start an explicit parallel pool. Values greater than \code{1} require MATLAB's Parallel Computing Toolbox; \code{0} is invalid.
\item \code{--policy}: policy identifier. The script reads the resolved run graph under \code{models/simulink/<simulator_id>/plans/<policy_id>/}.
\item \code{--overwrite}: mark all selected runs as \code{not_run} and materialize them again.
\item \code{--rerun-failed}: mark only selected runs currently recorded as \code{failed} as \code{not_run} and materialize them again.
\item \code{--raise-on-errors}: fail immediately instead of recording \code{failed} status.
\item \code{--debug}: create an additional folder \code{runs/<run_id>/debug/} containing \code{input_signals.mat} and \code{raw_simulation.pickle}.
\item \code{--run-id}: materialize only the specified \code{RUN_ID}. The run must appear in the resolved run graph for the selected \code{--policy}.
\item \code{--runs-root}: optional base directory for run artifacts. When set, each \termSimulator writes to \code{RUNS_ROOT/<simulator_id>/runs/} instead of \code{models/simulink/<simulator_id>/runs/}. This is intended for local NVMe scratch storage.
\item \code{--matlab-cache-root}: optional base directory for MATLAB/Simulink generated cache files. If omitted, MATLAB uses its normal cache and preference locations.
\item \code{--profile-timing}: write per-phase timing records to \code{profile_timing.jsonl} in the selected run root.
\item \code{--compute-features}: compute \code{features.json}. If feature names are provided, they must match the feature names defined by the \termSimulator-specific \code{features.py}.  By default, no features are computed.
\end{itemize}

The environment variable \code{SIMSCAPE_CUSTOM_PATH} must also be defined to the custom Simscape blocks.
For example:

\begin{DocCode}
SIMSCAPE_CUSTOM_PATH=/csem/divr/users/tbe/repo/tsENV/simscape_custom
\end{DocCode}

\section*{Inputs and Source of Truth}

For each \termSimulator under \code{models/simulink/<simulator_id>/}, the script requires:

\begin{itemize}
\item \code{plans/<policy_id>/run_nodes.jsonl}: the resolved list of runnable run recipes. It is the source of truth for \code{run_id}, \code{recipe_hash}, \code{kind}, \code{family_id}, \code{baseline_parameters}, changed parameter, intervention value, and intervention time.
\item \code{plans/<policy_id>/run_edges.jsonl}: the resolved graph relationships among runs. It is the source of truth for which intervention belongs to which baseline and which time-zero/static-change run belongs to which intervention.
\item \code{simulink_model_original.mdl}
\item \code{generated/metadata.json}: generated Simulink metadata, including the exposed parameter set and intervention block map.
\item \code{experiment_config.json}: source of truth for \code{sampling_rate_hz}, \code{end_time_input_s}, \code{observable_signals}, \code{signal_type}, and legal exposed-variable domains used for final validation before simulation.
\item \code{features.py}: optional. Used only when \code{--compute-features} is passed.
\item \phantomsection\label{sec:model-record-json-schema}\code{runs/model_record.json}: runtime inventory of materialized, pending, or failed runs. It is a flat object keyed by \code{run_id}. Each entry represents one materialized run node from a resolved run graph.
\end{itemize}

Schema:

\begin{DocCode}
{
  "<run_id>": {
    "run_type": "baseline|intervention|time0_baseline",
    "family_id": "<family_id>",
    "recipe_hash": "<32-hex-hash>",
    "status": "not_run|success|failed",
    "timestamp": "...",
    "last_policy_id": "<policy_id>",
    "class_internal": "gravity|mass|...|no_intervention|",
    "class_agent_facing_name": "gravity|mass|...|no intervention|"
  }
}
\end{DocCode}

The \code{recipe_hash} field is copied from \code{run_nodes.jsonl}.
The runtime inventory does not define the recipe; it only records the materialization status of a recipe whose canonical definition lives in the resolved run graph.

\section*{Internal Steps}

The code validates inputs, reconciles \code{model_record.json}, and then materializes selected runs.
The following applies to all run kinds: baseline, intervention, and time-zero/static-change runs.
Each run is materialized independently and tracked independently in \code{model_record.json}.

\subsection*{Validation Between \code{metadata.json}, \code{experiment_config.json}, and \code{description_levels.json}}

The stage validates the checks described in \hyperref[sec:environment-validation-rules]{the environment validation rules}.

\subsection*{Reconciliation Flow}

The script reconciles \code{run_nodes.jsonl} with \code{runs/model_record.json} as follows:

\begin{enumerate}
\item Load the resolved run nodes for \code{--policy} and build a map:
\begin{DocCode}
run_id -> recipe_hash
\end{DocCode}
\item Validate that every requested \code{run_id} has a unique \code{recipe_hash}, a valid \code{run_type}, and a recipe that satisfies the hard constraints in \code{experiment_config.json}.
\item For every run node in the selected plan, ensure that \code{model_record.json} contains a corresponding entry. Missing entries are created with status \code{not_run}.
\item If \code{--overwrite} is passed, mark every selected run as \code{not_run}.
\item If \code{--rerun-failed} is passed, mark only failed selected runs as \code{not_run}.
\item If \code{--run-id} is passed, restrict all later reconciliation and materialization to that single run.
\item If a run is currently marked as \code{success}, downgrade it to \code{not_run} if \code{runs/<run_id>/data.parquet} does not exist or if \code{model_record.json::<run_id>.recipe_hash} does not match \code{run_nodes.jsonl::<run_id>.recipe_hash}.
\item If a run is set to \code{not_run}, delete \code{runs/<run_id>/} before re-materialization.
\item By default, do not delete run folders that are outside the selected plan. Since run IDs are content-addressed, the same run may be reused by multiple policies. Pruning unknown folders is allowed only under an explicit cleanup flag.
\end{enumerate}

If no selected run remains in \code{not_run}, the stage rewrites \code{model_record.json} and exits without launching MATLAB.

\subsection*{Simulation Flow}

After reconciliation, the stage executes every selected run marked as \code{not_run}.
The simulation pipeline consists of five main steps, all defined in \code{shared/simulation.py}:

\begin{enumerate}
\item Simulink simulation: \code{raw_simulation = simulate_recipe(recipe, observable_signals)}.
The resolved node supplies:
\begin{itemize}
\item \code{kind}: one of \code{baseline}, \code{intervention}, or \code{time0_baseline}.
\item \code{baseline_parameters}: required simulator workspace values.
\item \code{intervention}: object with \code{parameter}, \code{value}, and \code{time}.
\item \code{end_time_input_s}: copied from \code{experiment_config.json::end_time_input_s}.
\end{itemize}

The top-level \code{kind} determines how the simulator applies the intervention.
Baseline nodes have no intervention; intervention nodes apply the changed value at \code{intervention.time}; time-zero/static-change nodes apply the changed value from time zero.
If the lower-level runtime call uses an internal \code{intervention_mode} field, Stage: Simulate derives it from \code{kind}; it must not read \code{recipe.intervention.mode}.

Internally, the function copies \code{simulink_model_original.mdl} to \code{runs/<run_id>/simulink_model.mdl}, assigns workspace values from \code{recipe.baseline_parameters}, applies \code{end_time_input_s} and \code{local_solver_step_size = 1/sampling_rate_hz}, calls \code{sim_the_model.m}, and keeps only the configured observable signals.

\item If requested, call \code{features.py::compute_problem_specific_features(raw_simulation[:end_time_input_s])} and save the result as \code{features.json}. Missing scalar features are stored as JSON \code{null}; missing list-valued features are stored as empty lists.

\item \code{df = resample_signal_dict(raw_simulation, signal_type, sampling_rate_hz)} validates continuous raw signals, preserves impulse-like events with the configured event handling, and returns a dataframe.
The first timestamp is expected to be \code{dt = 1/sampling_rate_hz}; the last point must be smaller than \code{end_time_input_s}.

\item \code{serialize(df, run_id)} saves the dataframe in \code{runs/<run_id>/data.parquet}. All signal columns and the serialized \code{time} column are stored with \code{float32} precision.

\item \code{validate(run_id)} reloads the saved artifact and checks timestamp spacing, column order, \code{float32} storage, minimum length, expected sample count, and absence of \code{NaN} or \code{inf} values.
\end{enumerate}

\subsection*{MATLAB Parallel Execution and Logging}

When \code{--matlab-workers 1} is used, Stage: Simulate starts one MATLAB engine session and materializes pending runs serially.
The console prints one \code{Simulating <kind> <run_id>...} line before each run.

When \code{--matlab-workers N} is greater than \code{1}, Stage: Simulate starts one MATLAB engine session, creates or reuses a MATLAB \code{parpool} with up to \code{N} workers, and dispatches prepared run jobs to the pool.
This is MATLAB worker parallelism, not Python process parallelism.
It requires MATLAB's Parallel Computing Toolbox and uses the active MATLAB local cluster profile.
If MATLAB reports that the profile has a smaller \code{NumWorkers} limit than the requested \code{N}, the run fails before simulations start.
For example, a \code{Processes} profile with \code{NumWorkers = 10} rejects \code{--matlab-workers 20}.
The configured limit can be inspected in MATLAB with:

\begin{DocCode}
c = parcluster("Processes");
c.NumWorkers
\end{DocCode}

and changed, if the local machine and license can support it, with:

\begin{DocCode}
c = parcluster("Processes");
c.NumWorkers = 20;
saveProfile(c);
\end{DocCode}

The stage first prepares isolated temporary workspaces for all pending runs, each containing a rewritten \code{simulink_model.mdl}, \code{sim_the_model.m}, and \code{time_varying_parameters.mat}.
It then submits those jobs to MATLAB in chunks.
By default the chunk size is \code{10 * --matlab-workers}; it can be overridden with:

\begin{DocCode}
TSENV_MATLAB_PARPOOL_CHUNK_SIZE=20
\end{DocCode}

Chunking is used because MATLAB returns simulation result objects to Python only after a submitted MATLAB batch returns.
Without chunks, a long run may look silent even though MATLAB workers are busy.
The MATLAB helper stores the chunk return as a cell array of scalar job-result structs so MATLAB Engine can transfer the results back to Python.
Python mirrors MATLAB \code{stdout} and \code{stderr} through \code{io.StringIO}-compatible streams, which is required by MATLAB Engine and allows the terminal to show MATLAB progress messages.
With chunks enabled, the expected console output is:

\begin{DocCode}
Running 1374 simulations with MATLAB parpool (10 workers).
Using MATLAB parpool with 10 workers.
Preparing 1374 MATLAB parpool job workspaces...
Prepared 1374 MATLAB parpool jobs; submitting 14 chunks of up to 100.
Submitting MATLAB parpool chunk 1/14 (100 jobs; completed 0/1374).
Submitted 100 MATLAB parpool jobs (0/1374 already complete before this chunk).
completed 1/1374 chunk 1/100 run_id=<run_id> status=success
...
Finished MATLAB parpool chunk 1/14; processed 100/1374 jobs.
\end{DocCode}

The \code{completed X/Y} lines are emitted by MATLAB as \code{fetchNext} receives worker results.
After a chunk returns, Python extracts signals, resamples, serializes \code{data.parquet}, validates, applies the status to \code{model_record.json}, and persists the registry.
Therefore \code{data.parquet} counts and \code{model_record.json} advance chunk-by-chunk, not at every individual MATLAB worker completion.
If the terminal shows no per-run output while \code{MATLAB -parallelserver} workers are consuming CPU, MATLAB is still inside the currently submitted chunk.
Use a smaller \code{TSENV_MATLAB_PARPOOL_CHUNK_SIZE} when faster visible registry/artifact progress is more important than submission overhead.

More workers are not expected to produce a linear speedup.
Only the MATLAB simulation batch is parallelized; Python preparation, workspace rewriting, signal extraction, resampling, serialization, validation, registry persistence, MATLAB startup, parpool startup, and worker coordination still cost wall-clock time.
Short simulations are especially sensitive to that fixed overhead.
In practice, small benchmark subsets may show faster MATLAB chunk execution but similar or slower end-to-end wall time.
Large policies amortize the fixed overhead better, so a stable low worker count such as \code{--matlab-workers 2} can be faster for a full policy even when it is not faster on a 20-run smoke test.
Very high worker counts can become slower or unstable because MATLAB workers compete for memory, disk/cache access, Simulink/Simscape initialization, and license/profile resources.

Use \code{--profile-timing} to compare worker counts on the target machine.
The end-to-end wall time should be compared together with \code{profile_timing.jsonl} phases:
\code{matlab_parpool_simulations} measures the submitted MATLAB chunk time, while \code{parallel_materialization} includes preparation and Python-side post-processing.
For a fair test, run the same policy into separate \code{--runs-root} directories and compare successful \code{data.parquet} counts as well as wall time.

\section*{Output Artifacts}

By default, materialized artifacts are stored under:

\begin{DocCode}
models/simulink/<simulator_id>/runs/<run_id>/
\end{DocCode}

When \code{--runs-root} is provided, artifacts are stored under:

\begin{DocCode}
<RUNS_ROOT>/<simulator_id>/runs/<run_id>/
\end{DocCode}

Each successful run directory contains:

\begin{itemize}
\item \code{recipe.json}: the exact canonical recipe copied from \code{run_nodes.jsonl}.
\item \code{data.parquet}: the materialized time series.
\item \code{simulink_model.mdl}: the exact Simulink model used to generate this run.
\item \code{features.json}: optional problem-specific feature dictionary computed from \code{observable_signals}. This file is omitted when \code{--compute-features} is not passed.
\end{itemize}

If \code{--debug} is passed, each successful run directory also contains:

\begin{itemize}
\item \code{debug/input_signals.mat}: MATLAB debug payload storing \code{TimeVaryingParameters}.
\item \code{debug/raw_simulation.pickle}: exact Python object returned by \code{simulate_recipe(...)}.
\end{itemize}

\code{model_record.json} is rewritten under the run root and serves as the runtime inventory of completed, pending, or failed run IDs.
Any validation error or simulation error records a failed run unless \code{--raise-on-errors} is passed.

\section*{Validation Rules}

In addition to run-specific validation, the stage enforces:

\begin{itemize}
\item every selected \code{run_id} must appear in \code{runs/model_record.json};
\item every \code{success} entry for a selected run must have a corresponding \code{runs/<run_id>/data.parquet} artifact;
\item every stored \code{recipe_hash} in \code{model_record.json} must match the \code{recipe_hash} in \code{run_nodes.jsonl};
\item every persisted \code{recipe.json} must match the selected run node's canonical recipe;
\item if MATLAB worker parallelism is enabled, materializing the same selected runs with one worker and with multiple workers must produce equivalent \code{recipe.json}, \code{data.parquet}, and success/failure records;
\item run folders outside the selected plan must not be deleted unless an explicit cleanup mode is enabled.
\end{itemize}

\section*{Troubleshooting: MathWorks Online Licensing State}

If Stage: Simulate cannot start MATLAB even though the MATLAB installation is present, check for stale MathWorks online-licensing state in the user's home directory.
This has previously affected \code{L7161}: MATLAB was unable to reuse the existing online license state until the local MathWorks licensing, credentials, and ServiceHost state were moved aside and regenerated by an interactive MATLAB login.

First inspect MATLAB and MathWorks background processes scoped to the current user:

\begin{DocCode}
pkill -TERM -u "$USER" -f 'MATLAB|matlab|MathWorks|MathWorksServiceHost|MATLABWindow|matlabwindow|mvm|xvfb|fluxbox'
\end{DocCode}

This could be enough, altough if not, we need to delete some cretdential files and regenerate them.
