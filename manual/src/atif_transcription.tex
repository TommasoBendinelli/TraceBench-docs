\docTitle[Agent Trajectory Schema]{Agent Trajectory Schema}
\phantomsection\label{docstart:atif_transcription}
This is the canonical format used in \name{}. 
Each agent produces its own format, and this is a way of standardizing stuff.
Our format is based on ATIF v1.6 \url{https://github.com/harbor-framework/harbor/blob/main/rfcs/0001-trajectory-format.md}.
We have a script that converts everything in this format from any agent.
We additionally have a light version of the format, to easy analytics. 
The light version is stripped of heavy metadata.

\subsection{Technical Documentation}
\begin{DocCode}
python workflows/rollout/export_atif_trajectory.py [<agentic_run_id>] [--path PATH]
\end{DocCode}
Note that only one of \code{<agentic_run_id>} or \code{--path} may be passed.
The \code{agentic_run_id} resolves to:
\begin{DocCode}
terminal-bench/runs/<agentic_run_id>
\end{DocCode}

\subsection{Inputs}
This script takes as input:
\begin{itemize}
  \item \code{scenario_info.json} to read information regarding \code{agent_id}, \code{question_id}, \code{tag}
  \item \code{terminal-bench/runs/<run_id>/question_0/question_0.1-of-<run_id>/agent_logs/*.json}.
  For each platform type, there is a different parsings. Currently supported:
  \begin{itemize}
    \item codex
    \item gemini-cli
    \item claude-code
    \item opencode
  \end{itemize}
\end{itemize}

And produces
\begin{itemize}
  \item \code{terminal-bench/runs/<run_id>/question_0/question_0.1-of-<run_id>/agent_logs/atif_processed/atif_trajectory.json}
  \item \code{terminal-bench/runs/<run_id>/question_0/question_0.1-of-<run_id>/agent_logs/atif_processed/atif_trajectory_light.json}
\end{itemize}
\section*{\texorpdfstring{\titlecode{atif_trajectory.json}}{atif_trajectory.json} schema}

The top-level object has the following shape:

\begin{DocCode}
{
  "tag": "...",
  "question_id": "...",          # matches the question id
  "agent_id": "...",             # matches the scenario id
  "session_id": "...",           # matches the run id
  "final_metrics": { ... },      # aggregate metrics described below
  "is_context_compacted": false, # true when the context has been compacted
  "steps": [ ... ]               # interaction turns
}
\end{DocCode}


\section*{\texorpdfstring{\titlecode{final_metrics}}{final_metrics}}

\begin{DocCode}
total_prompt_tokens =
  sum(input_cached_prompts_i + input_non_cached_prompts_i)

total_completion_tokens =
  sum(completion_tokens_i)

total_cached_tokens =
  sum(input_cached_prompts_i)

non_cached_total =
  total_prompt_tokens - total_cached_tokens

total_cost_usd =
  non_cached_total * cost.input_token / 1_000_000
  + total_cached_tokens * cost.cached_token / 1_000_000
  + total_completion_tokens * cost.completion_token / 1_000_000
\end{DocCode}

Assert that \code{non_cached_total} is not negative.
Costs are agent-specific and defined in \hyperref[docstart:agent_profiles]{Agent Profiles Reference}.

\begin{itemize}
\item \code{total_steps}: equal to the total number of steps
\item \code{total_duration}: \code{sum(steps[i].duration)} over steps whose \code{source} is \code{AGENT}
\item \code{total_tool_duration}: \code{sum(steps[i].observation[j].duration)}
\end{itemize}

\section*{\texorpdfstring{\titlecode{steps}}{steps}}


\begin{itemize}
\item \code{step_id}: \code{int}
\item \code{timestamp}: when the final text of the step is emitted. 
\item \code{duration}: duration in seconds between the previous step timestamp and the current step timestamp. Only applicable if the message source is \code{AGENT}
\item \code{source}: one of \code{USER}, \code{AGENT}, or \code{SYSTEM}. \code{SYSTEM} is triggered, for instance, when we run a cron job (Should not happen in our case).
\item \code{message}: \code{[content type]} str
\item \code{reasoning_content}: optional field for models that support it
\item \code{tool_calls}: array of \code{ToolCall}
\item \code{observation}: list of \code{Observation}
\item \code{metrics}: \code{prompt_tokens}, \code{completion_tokens}, \code{cached_tokens}. Note that \code{completion_tokens} includes \code{thoughts} too.
\end{itemize}

\section*{\texorpdfstring{\titlecode{ToolCall Scheme}}{ToolCall Scheme}}
\begin{itemize}[leftmargin=2em]
    \item \code{tool_call_id}
    \item \code{function_name}: agent-specific
    \item \code{arguments}
\end{itemize}

\section*{\texorpdfstring{\titlecode{Observation Scheme}}{Observation Scheme}}
\begin{itemize}[leftmargin=2em]
    \item \code{source_call_id}: must match a previous call id
    \item \code{content}: output or result
    \item \code{timestamp}: time when the tool call is returned.
    \begin{itemize}
      \item For \code{gemini-cli} session json it's \code{messages[i].toolCalls[j].timestamp}
    \end{itemize}
    \item \code{duration}: duration in seconds between \code{steps[i].timestamp} and \code{steps[i].observation[j].timestamp}
\end{itemize}

\section*{\texorpdfstring{\titlecode{atif_trajectory_light.json}}{atif_trajectory_light.json}}

The light trajectory is a reduced projection of \code{atif_trajectory.json}.
It contains only:

\begin{itemize}
\item \code{agent_id}: copied unchanged from the full trajectory
\item \code{session_id}: copied unchanged from the full trajectory
\item \code{steps}: reduced interaction turns
\end{itemize}
Each element of \code{steps} keeps only:
\begin{itemize}
\item \code{step_id}
\item \code{source}
\item \code{message}
\item \code{tool_calls}
\item \code{observation}
\end{itemize}

\section*{Semantic rules}
\begin{itemize}
  \item Computed durations cannot be negative. This includes \code{steps[i].duration}, \code{steps[i].observation[j].duration}, \code{total_duration}, and \code{total_tool_duration}.
  \item If the original format exposes already the cumulative count, our computation and the cumulative count must match
\end{itemize}
In case these are not respected, the conversion will fail
