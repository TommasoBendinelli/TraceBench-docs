\section*{\texorpdfstring{\titlecode{model_run_specs.json}}{model_run_specs.json} Schema}
\label{sec:model-run-specs-schema}

This file defines the planned run topology for one model.
It is authored by humans/agents and consumed by Stage: Simulate.

It defines:
\begin{itemize}
\item the baseline runs
\item the intervention child runs derived from each baseline
\item the synthetic time-zero baseline runs associated with each child
\item the hashes used to keep the planned runs aligned with the materialized runs on disk
\end{itemize}

\section*{Run Kinds}

The current contract uses three run kinds:

\begin{itemize}
\item A baseline run is the simulation defined by one entry of \code{baseline_parameters}.
\item An intervention child run is the simulation obtained by changing exactly one of \code{baseline_parameters} that is also in \code{experiment_config.json:exposed_variables:parameters}.
\item A time-zero baseline run is the synthetic run associated with one child intervention, where the same intervention is treated as active from time zero.
\end{itemize}

\section*{Top-Level Shape}

\code{model_run_specs.json} must be a non-empty JSON object keyed by \code{baseline_uuid}.

Each top-level entry defines exactly one baseline and contains:
\begin{itemize}
\item \code{baseline_parameters}
\item \code{baseline_parameters_hash}
\item \code{children}
\end{itemize}

A minimal shape is:

\begin{DocCode}
{
  "<baseline_uuid>": {
    "baseline_parameters": {
      "simulation_specific_parameter_0": 1.0,
      "simulation_specific_parameter_1": 2.0,
    },
    "baseline_parameters_hash": "<32-hex-hash>",
    "children": {
      "<intervention_uuid>": {
        "intervention_time": 3.0
        "parameters": {
          "simulation_specific_parameter_0": 1.5
        },
        "parameter_hash": "<32-hex-hash>",
        "time0_baseline_hash": "<32-hex-hash>",
        "time0_baseline_uuid": "<32-hex-hash>",
        "direction": "increase"
      }
    }
  }
}
\end{DocCode}

\section*{Field Definitions}

\subsection*{Top-Level Object}

The top-level object:
\begin{itemize}
\item must be non-empty
\item is keyed by \code{baseline_uuid}
\end{itemize}

Each \code{baseline_uuid} identifies one planned baseline run.

\subsection*{Baseline Entry}

Each baseline entry must define exactly these fields:
\begin{itemize}
\item \code{baseline_parameters}: object
\item \code{baseline_parameters_hash}: 32-character hexadecimal string (computed by \code{refresh_model_run_spec_hashes.py})
\item \code{children}: object keyed by \code{intervention_uuid}
\end{itemize}

\subsection*{Baseline Parameters}

\code{baseline_parameters} contains the persisted baseline payload for one run. 
It must include all \code{experiment_config.json:exposed_variables:parameters}, \code{experiment_config.json:exposed_variables:initial_state}.


All values in \code{baseline_parameters} are numeric in the current contract.
\subsection*{Children}

\code{children} is an object keyed by \code{intervention_uuid}.

Each child entry must define exactly these fields:
\begin{itemize}
\item \code{parameters}: object
\item \code{parameter_hash}: 32-character hexadecimal string (computed by \code{refresh_model_run_spec_hashes.py}) or \code{null} for skipped children
\item \code{time0_baseline_uuid}: 32-character lowercase hexadecimal UUID string for the associated synthetic time-zero baseline, or \code{null} for skipped children
\item \code{time0_baseline_hash}: 32-character hexadecimal string (computed by \code{refresh_model_run_spec_hashes.py}) or \code{null} for skipped children
\item \code{direction}: \code{"increase"} or \code{"decrease"}
\item \code{intervention_time}
\end{itemize}

Each child entry defines:
\begin{itemize}
\item one intervention child run, identified by \code{intervention_uuid}
\item one associated synthetic time-zero baseline run
\end{itemize}

\subsection*{Child Parameters}

The child \code{parameters} object must contain exactly one field.

That field must be one of \code{experiment_config.json:exposed_variables:parameters}. For runnable children, the value is numeric and respects:
\begin{itemize}
  \item \code{experiment_config.json:exposed_variables:parameters:allowed_intervals} 
  \item \code{experiment_config.json:exposed_variables:parameters:}\termMinSRDDistance minimum \termSRD from the base parameter
  \item \code{experiment_config.json:exposed_variables:parameters:}\termMinAbsDist absolute distance from the base parameter
\end{itemize}

For skipped children, that single value is \code{null}; \code{direction} records whether the skipped child is the missing increase-side or decrease-side sample.

Example:

\begin{DocCode}
{
  "parameters": {
    "viscous_damping": 0.3
  }
}
\end{DocCode}

\section*{UUIDs}

\code{baseline_uuid}, \code{intervention_uuid}, and \code{time0_baseline_uuid} are
persisted as 32-character lowercase hexadecimal UUID strings without hyphens.

They are the canonical run identities used across downstream stages.

In the current contract:
\begin{itemize}
\item every \code{baseline_uuid} must be unique within the file
\item every \code{intervention_uuid} must be unique within the file
\item every non-null \code{time0_baseline_uuid} must be unique within the file
\end{itemize}

\section*{Hashes}

Hashes are used to keep planned runs aligned with materialized runs.

All hash fields are represented as 32-character hexadecimal strings.

The exact canonicalization and digest procedure is defined by \code{refresh_model_run_spec_hashes.py}.
At a semantic level, the three hash fields mean:

\begin{itemize}
\item \code{baseline_parameters_hash} is the identity of the baseline run defined by \code{baseline_parameters}
\item \code{parameter_hash} is the identity of the child run defined by the parent baseline together with the child \code{parameters} and \code{intervention_time} attributes.
\item \code{time0_baseline_hash} is the identity of the synthetic time-zero baseline associated with that child run
\end{itemize}

\subsection*{Hash Computation}

In the current implementation, hashes are recomputed by
\code{refresh_model_run_spec_hashes.py} using the helper functions
\code{compute_parameters_hash}, \code{compute_child_parameters_hash}, and
\code{compute_time0_baseline_hash} from
\code{shared/interface/model_record_json.py}.

The refresh flow is:
\begin{enumerate}
\item load the stored \code{model_run_specs.json} object
\item parse each baseline entry and its \code{baseline_parameters}
\item normalize numeric-like values before rewriting the tree payload
\item rebuild the canonical tree payload
\item recompute all three hash fields from that normalized payload and rewrite them into the file
\end{enumerate}

The current normalization rules are:
\begin{itemize}
\item integers remain integers
\item finite floats that are mathematically integral are rewritten as integers
\item \code{0.0} is rewritten as \code{0}
\item numeric strings may be rewritten to numeric JSON values before hashing
\item non-finite numeric values are rejected
\item UUID strings are normalized to the persisted 32-character lowercase hexadecimal form
\end{itemize}

Hashing itself uses:
\begin{itemize}
\item canonical JSON with sorted keys and compact separators
\item SHA-256 as the digest
\item the first 32 hexadecimal characters of that digest as the stored hash
\end{itemize}

The three hash payloads are:
\begin{itemize}
\item \code{baseline_parameters_hash}: SHA-256 over the full persisted \code{baseline_parameters} object
\item \code{parameter_hash}: SHA-256 over
\begin{DocCode}
{
  "intervention_time": 12.34,
  "parent_parameters_hash": "<baseline_parameters_hash>",
  "parameters": { ...single child parameter... }
}
\end{DocCode}
\item \code{time0_baseline_hash}: SHA-256 over
\begin{DocCode}
{
  "parameter_hash": "<parameter_hash>",
  "kind": "time0"
}
\end{DocCode}
\end{itemize}


The refresh script does not trust previously stored hash strings. It recomputes all hash
fields from the normalized payload and then rewrites the file.

\section*{Semantic Validation Rules}

These rules are enforced when hashes are refreshed by \code{refresh_model_run_spec_hashes.py [--repair]}.
If \code{--repair} is passed, the script will try to repair these errors on its own. 
Without the flag, or when it's not possible, an error will be raised.
\begin{itemize}
\item the top-level object must be non-empty
\item each baseline entry must contain \code{baseline_parameters}, \code{baseline_parameters_hash}, and \code{children}
\item all values in \code{baseline_parameters} must be numeric
\item each child entry object must define \code{intervention_time}; it must satisfy \code{0 < intervention_time < experiment_config.json::end_time_input_s}
\item each child entry must contain \code{parameters}, \code{parameter_hash}, \code{time0_baseline_uuid}, \code{time0_baseline_hash}, and \code{direction}
\item each child \code{parameters} object must contain exactly one field
\item for runnable children, the intervened field value must differ from the parent baseline value with an absolute change that strictly exceeds \code{experiment_config.json::exposed_variables.parameters.<parameter>.}\termMinAbsDist
\item for runnable children, the intervened field value must differ from the parent baseline value with an \termSRD that strictly exceeds \code{experiment_config.json::exposed_variables.parameters.<parameter>.}\termMinSRDDistance
\item for skipped children, the single child value must be \code{null}; \code{parameter_hash}, \code{time0_baseline_uuid}, and \code{time0_baseline_hash} must all be \code{null}
\item each parent must contain at least two child for each parameter listed in \code{experiment_config.json::exposed_variables::parameters}. 
One bigger than the baseline value and one smaller than the baseline value. If the child cannot be sampled because the effective interval to sample it is empty due to the constraints, then its value should be \code{null}, the child must still persist with the corresponding \code{direction}, and it is skipped during simulation.
\item Each baseline must differ from every other baseline in at least one parameter listed under \code{experiment_config.json::exposed_variables.parameters} or in \code{experiment_config.json::exposed_variables.initial_state}.
For that parameter, both the absolute difference and \termSRD must be greater than or equal to the parameter's \code{min_abs_dist}/5 and \code{min_srd_distance}/5, respectively.
\item all UUIDs must be unique across the file
\item all non-null hashes must be unique across the file, including \code{baseline_parameters_hash}, \code{parameter_hash}, and \code{time0_baseline_hash}
\end{itemize}

\section*{Artifact Policy}

\begin{itemize}
\item \code{model_run_specs.json} is authored and modified by humans
\item the hash fields are refreshed by \code{refresh_model_run_spec_hashes.py} and should not be edited manually
\item if \code{model_run_specs.json} is newer than \code{model_record.json}, Stage: Simulate refreshes the hashes first and then continues reconciliation
\item this file is a planning artifact only; it does not materialize runs by itself
\end{itemize}
